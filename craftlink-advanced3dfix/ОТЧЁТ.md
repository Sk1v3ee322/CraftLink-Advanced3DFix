## ЧАСТЬ I. CraftLink — экспорт из FilmCraft в EffectCraft и обратная связь

### 1.1 Что видит пользователь

1. В FilmCraft выделяет клипы на таймлайне → правый клик.
2. **Replace with EffectCraft Composition** — заменяет выделение одним «связанным» клипом и
   открывает выделение композицией в EffectCraft.
   **Send to EffectCraft…** — то же самое, но таймлайн FilmCraft не трогает (одноразовая отправка).
3. Правит в EffectCraft (Glow, маски, анимация…).
4. Примерно через секунду после последней правки — или сразу по **File ▸ Save** — EffectCraft
   перерендеривает композицию **поверх того же мастер-файла**. Сохранять не обязательно.
5. FilmCraft замечает изменение и перечитывает мастер: на таймлайне уже новая картинка.

Связь хранится в реальном файле на диске, поэтому переживает перезапуск любого из приложений.

### 1.2 Как это устроено

```
FilmCraft: выделение клипов
   │
   ├─ nest_selection_for_bridge ......... вложенная секвенция, сдвинутая к тику 0
   ├─ materialize_generators_for_export . процедурные демо-генераторы запекаются в MP4
   ├─ export FCP7 XML ──────────────────► <имя>.xml
   ├─ write_manifest ───────────────────► <имя>.craftlink.json   (sidecar)
   └─ bake_linked_master ───────────────► CraftLink/<имя>.mov    (ProRes 4444 + alpha + PCM)
   │
   ├─ link_placed_clips_to_master ....... клипы таймлайна указывают на <имя>.mov
   └─ launch_or_notify_effectcraft ...... loopback в запущенный EffectCraft, иначе запуск
                                          effectcraft.exe <имя>.xml

EffectCraft: file.importTimeline
   ├─ импорт XML в композицию
   └─ register_import: Item.comment = "craftlink:{...}"   (переживает сохранение проекта)

правка в EffectCraft
   │
   ├─ через 1 с после последней правки (craftlink_tick) или по File ▸ Save (auto_sync)
   ├─ render_comp ──► <имя>.partial.mov ──► rename поверх <имя>.mov
   ├─ spool-файл: %TEMP%\CraftLink\reload-<pid>-<ms>.notify
   └─ опционально loopback: "craftlink.refresh"

FilmCraft: tick_media_refresh видит notice (опрос раз в 0.5 с, пока проект показывает связь)
   └─ start_media_scan ──► apply_media_stamps ──► перечитать <имя>.mov
```

Два независимых канала уведомления сделаны намеренно: spool-файл не требует ни сокета, ни токена,
ни порта и работает, даже если FilmCraft запущен без `--control`; loopback — просто ускоритель.

### 1.3 Форматы данных

**Обменный таймлайн — Final Cut Pro 7 XML** (`<xmeml version="4">`). Пишется
`filmcraft_interchange::export(..., Format::Fcp7Xml, ...)`, читается
`effectcraft_interchange::import`. Используются только элементы, которые обе стороны уже
поддерживают (`sequence`, `media/video`, `track`, `clipitem`, `file`, `transitionitem`, `filter`,
маркеры). Ничего специфичного для CraftLink в XML не добавлено — файл остаётся читаемым любым
потребителем FCP7 XML.

**Sidecar-манифест** `<имя>.craftlink.json` рядом с XML:

```json
{
  "craftlink": 1,
  "composition": "CraftLink Comp 01",
  "xml": "C:\\Projects\\Demo\\CraftLink Comp 01.xml",
  "render": "C:\\Projects\\Demo\\CraftLink\\CraftLink Comp 01.mov",
  "autoSync": true,
  "application": "FilmCraft"
}
```

Манифест опционален: обычный импорт XML без него ведёт себя как всегда и связи не создаёт.

**Хранение связи внутри EffectCraft** — в существующем поле комментария айтема композиции, одной
строкой с префиксом `craftlink:`. Это **не требует изменения схемы проекта** и сохраняется вместе с
`.ecproj`. Комментарий без префикса никогда не трактуется как связь.

### 1.6 Live-link: правки уезжают без сохранения

| Часть | Где | Что делает |
| --- | --- | --- |
| `Session::craftlink_live: LiveSync` | `lib.rs`, `craftlink.rs` | состояние дебаунса `{dirty, since, seen, comp, rendered}` |
| `craftlink_note_change(id)` | `session/dispatch.rs` | после команды, продвинувшей `revision`: взводит связь активной композиции; open/revert/import только помечают ревизию прочитанной |
| `craftlink_tick(now)` | `ui-egui/src/app/frame.rs` | когда правок нет `LIVE_DELAY` (1.0 с) — один «тихий» `spawn_render` |
| `craftlink_live_pending()` | `ui-egui/src/app/frame.rs` | держит repaint раз в 120 мс, пока рендер должен состояться |
| `watches_linked_master(project)` | FilmCraft `media_watch.rs` | проект с мастер-файлом внутри папки `CraftLink` опрашивает spool каждые 0.5 с |

Правила, которые пришлось соблюсти:

- Перерендеривается только композиция, **активная** в момент правки; переключение композиций
  посреди правки не рендерит вторую.
- Один рендер за раз: правка во время рендера запоминается и рендерится после, а не копится.
- `autoSync: false` отключает и live-link; такая связь рендерится только по `file.craftlinkSync`
  и File ▸ Save.
- Live-рендер «тихий» (без тоста); отчитываются только явная синхронизация и сохранения.
- У движка нет часов, поэтому дебаунс ведёт фронтенд, передавая монотонное `AppClock::now()`.

### 1.7 Попутно исправленный баг: пропавший fade-out

**Симптом.** После отправки выделения в EffectCraft пропадал fade-out в конце **последнего
выделенного клипа**.

**Причина.** Переход может стоять на границе выделения: исходящая сторона выделена, входящая — нет.
Старая реализация копировала переход только если выделены **обе** стороны, поэтому граничный
переход терялся и клип лишался затухания.

**Исправление.** `nest_selection_for_bridge` теперь сохраняет каждый переход, у которого хотя бы
одна сторона в выделении, а отсутствующую сторону превращает в «чёрный»:

| Исходный | В выделении | Результат |
| --- | --- | --- |
| `from = A`, `to = B` | только A | `from = A`, `to = None` → `end-black` (fade-out) |
| `from = A`, `to = B` | только B | `from = None`, `to = B` → `start-black` (fade-in) |
| `from = None`, `to = B` | B | без изменений |
| `from = A`, `to = None` | A | без изменений |
| обе стороны вне выделения | — | отбрасывается |

Затем переход **обрезается по границам выделенного клипа**, но только если он действительно потерял
вторую сторону; переход, у которого обе стороны в выделении (cross dissolve между двумя выделенными
клипами), копируется целиком. FCP7-писатель выдаёт `start-black` / `end-black`, а импортёр
EffectCraft уже отображает их в кейфреймы Opacity.

Регрессионные тесты: `boundary_transition_becomes_a_one_sided_fade`,
`a_cross_dissolve_between_two_selected_clips_keeps_both_sides`.

### 1.8 Прочее, что вошло в CraftLink-патч

- **Двойной клик по `.xml` в проводнике** открывает его в EffectCraft как таймлайн (раньше
  открывался только `.ecproj`). Также `file.import` теперь сам распознаёт `.xml/.fcpxml/.otio/
  .edl/.aaf/.omf` и отправляет их в импорт таймлайна — то есть drag-and-drop в окно тоже работает.
- **Обратное направление**: File ▸ Export ▸ **Send to FilmCraft…** (`file.sendToFilmCraft`) —
  экспорт XML + запуск/уведомление FilmCraft, симметрично прямому направлению.
- **Убран мелькающий консольный режим** у релизных сборок Windows:
  `#![cfg_attr(all(target_os = "windows", not(debug_assertions)), windows_subsystem = "windows")]`
  → `#![cfg_attr(target_os = "windows", windows_subsystem = "windows")]` в обоих `main.rs`.
  Иначе при запуске FilmCraft из EffectCraft на мгновение появлялось чёрное окно консоли.
- **`note_media_stamp`** — запоминает текущий размер/mtime файла как базовый. Нужно потому, что
  watcher намеренно считает переход `None → Some` за «не изменилось»; без этой базовой отметки
  сохранение в EffectCraft, произошедшее до первого планового скана FilmCraft, было бы пропущено.

### 1.9 Исправленная ошибка: первая «Отправка в EffectCraft» падала с `os error 3`

**Симптом.** В проекте, из которого ещё ничего не отправляли в EffectCraft, **первый** запуск моста
падал с голым `os error 3` (ERROR_PATH_NOT_FOUND) и ничего не записывалось. Вторая попытка
срабатывала, потому что папка к тому времени уже была.

**Причина.** `execute_bridge` пишет XML через `Services::write_file`, а он атомарный: пишет во
временный файл и переименовывает его в целевой. В отличие от `write_file_new`, он **не создаёт**
отсутствующие родительские папки. Папка ссылки (`<папка проекта>/CraftLink`) создавалась позже, внутри
`bake_linked_master`, то есть *после* записи XML — поэтому на свежем проекте первой записи было некуда
переименовываться.

**Исправление.** `craftlink_bridge.rs` создаёт родительскую папку перед записью XML:

```rust
if let Some(parent) = out_path.parent().filter(|d| !d.as_os_str().is_empty()) {
    std::fs::create_dir_all(parent)
        .map_err(|e| EngineError::Other(format!("cannot create {}: {e}", parent.display())))?;
}
```

Вместо голого кода ОС теперь выдаётся диагностика с путём.

Регрессионный тест: `the_first_bridge_run_creates_its_link_folder` — направляет сессию на путь
проекта, у которого папки `CraftLink` нет, вызывает `clip.sendToCraftLink` и проверяет, что записаны
и XML, и sidecar-манифест. Без исправления он падает с тем самым `os error 3`.

## ЧАСТЬ II. Layer Styles на 3D-тексте (как в After Effects)

### 2.1 В чём была проблема

Layer Styles (Stroke, Inner Shadow, Drop Shadow, Bevel, Satin, Overlays…) в EffectCraft считались
в **пространстве слоя** по его «плоскому» содержимому. Для 2D-слоя это правильно. Но 3D-текст с
**Geometry Options ▸ Extrusion Depth** — это уже не картинка, а геометрия: боковые грани, скос,
развёрнутая под камерой плоскость.

В старой сборке у такого слоя стилизованной картинки не было вовсе. В Advanced 3D `adv/scene.rs`
рисовал экструдированный текст или фигуру через `extruded_layer()` → `extruded_meshes()`; эта
функция возвращает **готовые цвета заливки/обводки на каждый меш** и к `styles::*` не обращается.
То есть Layer Styles экструдированного слоя молча терялись: ни обводки, ни теней (см. скриншот
«Old Version» в `screenshots/`). Экструзия — возможность именно Advanced 3D: в `compose.rs` режима
Classic 3D пути экструзии нет, так что проявиться это могло только там.

Per-character 3D упирался в ту же стену с другой стороны: оба рендерера строят его как по одной
плоскости на глиф (`adv/scene.rs` `card_layer()` и `compose.rs` `prepare_all()` для Classic зовут
`text::per_char_planes()`), а в старой сборке эти плоскости были просто раскрашенными глифами без
каких-либо проходов стилей — стили такого слоя на экран тоже не попадали.

Плоские 3D-карты (`card_layer()` → `blend_layer_buf()`) и 2D-слои через `styles::render()`
проходили, поэтому баг было легко не заметить: стили работали, пока не включались Geometry Options.

В After Effects стили рисуются **после** рендера слоя, то есть по его итоговому изображению в
кадре. Именно это и было воспроизведено.

### 2.2 Решение: два разных пути, по типу 3D-текста

**(а) Экструдированный текст и фигуры** — идут через 2D-путь композитинга Advanced 3D.

```
scene::extrusion_params(layer).is_some() && styles::active(layer)
        │
        ▼
styled_geometry() == true  →  needs_2d_composite() == true
        │
        ▼
draw_run: слой рендерится ОТДЕЛЬНО в свою текстуру (главная сцена — без него)
        │
        ├─ style_solo():  стили считаются по пикселям этого рендера
        └─ слой скрывается там, где главная сцена ближе (occlusion по depth-буферу)
        │
        ▼
2D-композитинг: track matte, Preserve Transparency, blend mode, opacity
```

Ключевой момент — **корректная работа с opacity**: в 2D-пути стили видят слой при полной
непрозрачности, а прозрачность гасит уже всю готовую «стопку» (тело + тени + обводки). Чтобы
сохранить это поведение, `style_solo` сначала **делит** пиксели на прозрачность слоя, считает
стили, затем **умножает** результат обратно. Дополнительно учтены `out_offset()` (region of
interest) и `opts.scale` (Half/Third/Quarter resolution), иначе стили уезжали бы при рендере в
половинном разрешении или в ROI.

**(б) Per-character 3D текст** (галочка Per-character 3D) — сюда 2D-путь не подходит: каждая буква
это отдельная плоскость со своей матрицей, и «общий» силуэт слоя в кадре не совпадает с суммой
плоскостей. Поэтому стили применяются **к каждой букве отдельно**:

```
text::per_char_planes()
    для каждого глифа:  нарисовать глиф → styles::styled_buf(...) → пуш (buf, matrix)
```

`styled_buf()` — новая маленькая обёртка в `styles.rs`: считает стили и сразу сплющивает
внешние проходы (Drop Shadow / Outer Glow) в один буфер, потому что плоскость в 3D-сцене — это
одна текстура, отдельные проходы туда не положить.

### 2.3 GPU: те же правила, но с read-back

Advanced 3D на GPU рисуется в сварочных буферах и композитится ядрами WGSL. Для стилейых
экструзий сделано так (`gpu::walk::draw_split`):

```
resolve_run(special layer)                      обычный рендер слоя
finish(...)                                     → GPU-изображение
download(...)                                   → пиксели на CPU  (read-back)
adv::style_solo(r, ctx, layer, img)             → CPU-проходы стилей
upload_image(...)                               → назад на GPU
occluded_image(..., iso.depth(), ...)           → скрыть за ближней геометрией
composite_iso_with(..., 1.0, matte3d)           → 2D-матт/блендинг
```

Для этого понадобились `adv3d::occluded_image()` (скрытие уже готовой картинки по depth-буферу
изолированного рендера) и аксессоры `Resolved::depth()` / `Resolved::size()`.

Стили остаются на CPU намеренно: это ровно те же проходы, что и у любого 2D-слоя, поэтому
картинка CPU и GPU совпадает. Цена — один read-back **только для таких слоёв** (экструзия +
включённые стили); обычные слои ничего не платят.

### 2.4 Что изменено в коде

| Файл | Изменение |
| --- | --- |
| `crates/render/src/three_d/adv.rs` | `styled_geometry()` (pub), `style_solo()` (pub), учёт opacity / ROI / scale, `blit()`; `needs_2d_composite()` включает новые слои; `split_run()` больше не отбрасывает стильные слои целиком |
| `crates/render/src/styles.rs` | новый `styled_buf()` — стили + сплющивание проходов в один буфер |
| `crates/render/src/text.rs` | `per_char_planes()` накладывает стили на плоскость каждого глифа |
| `crates/render/src/three_d/compose.rs` | только комментарий (+2 / −0): `prepare_all()` и так передаёт per-character 3D в `per_char_planes`, логика здесь не менялась |
| `crates/gpu/src/walk.rs` | `draw_split()`: finish → download → `style_solo` → upload → `occluded_image` |
| `crates/gpu/src/adv3d.rs` | новый `occluded_image()`, аксессоры `Resolved::depth()/size()` |
| `docs/architecture.md` | новый абзац в разделе **Layer styles** + правки в разделе GPU-композитинга |
| `docs/user/guides/add-an-effect.md` | одна строка для пользователя: стили следуют за отрендеренным 3D |

Отдельная деталь: `blit()` в `style_solo` кладёт готовый буфер стилей обратно в кадр по смещению
`-flat.offset - out_offset()`. Это то место, где проще всего ошибиться на единицу. Покрыто
косвенно, отдельного теста нет: `extruded_3d_text_takes_layer_styles` сравнивает число пикселей
обводки у экструзии и у той же надписи плоской картой (0.7–1.3×), поэтому сдвинутые стили вышли бы
из этого коридора; `styles_respect_render_scale` (существовавший раньше) фиксирует смещение на
половинном разрешении. Теста, который рисует экструзию внутри region of interest, нет — это
единственная ветка математики смещений, которую ревьюеру стоит прочитать глазами.

### 2.5 Тесты

**CPU** (`crates/render/src/tests/styles.rs`), все зелёные:

| Тест | Что проверяет |
| --- | --- |
| `extruded_3d_text_takes_layer_styles` | экструдированный текст + Stroke: красных пикселей обводки > 500 на Classic 3D, на Advanced карточке и на Advanced экструзии |

| `per_char_3d_text_takes_layer_styles` | per-character 3D + Stroke (Classic и Advanced) |

**GPU** (`crates/gpu/src/tests/adv3d.rs`):

| Тест | Результат |
| --- | --- |
| `gpu_styled_extrusions_match_cpu` | расхождение CPU vs GPU **0.000 %** пикселей (порог 2 %), max |Δ| = **0.0039** (≈1/255) |

Тест заодно утверждает, что слой со стилями **не** попадает в быстрый путь `prepare_adv_run` и
**попадает** в `split_adv_run` — то есть маршрутизация не «оптимизируется» обратно случайно.

### 2.6 Известные ограничения (честно)

- Стили на экструзии стоят один read-back на кадр **на такой слой**. Если в кадре десять
  экструзий со стилями — будет десять read-back. Для типичной композиции (1–3 текста) это
  незаметно, но это не «бесплатно».
- Per-character стили считаются **на каждую букву**, поэтому стиль, который по смыслу должен
  облегать всё слово (например, Drop Shadow с большим Distance), на перекрывающихся буквах
  выглядит иначе, чем в AE. Это осознанный компромисс: плоскости букв в 3D не образуют единого
  силуэта. Для «общего» силуэта слоя есть экструдированный (не per-character) путь.
- Inner Bevel по-прежнему подкрашивает сглаженный край поверх собственного цвета слоя — это
  **старое** поведение, не связанное с этой работой (записано в `docs/target-app-parity.md`).

## ЧАСТЬ III. Как проверить

### 3.1 Сборка

```powershell
# FilmCraft
cd filmcraft-0.20.1
cargo build --release -p filmcraft --features filmcraft/neural-voices
cargo test -p filmcraft-engine craftlink

# EffectCraft
cd ../effectcraft-0.24.1
cargo build --release -p effectcraft
cargo test -p effectcraft-render --lib
cargo test -p effectcraft-gpu
cargo test -p effectcraft-engine craftlink
```

Использованный тулчейн: `stable-x86_64-pc-windows-gnullvm` (MSVC `link.exe` в системе нет).

Две детали окружения, которые стоит знать:

- **`--features filmcraft/neural-voices`** — скрипт упаковки релиза
  (`packaging/windows/package.ps1`) собирает именно с этой фичей, а в
  `apps/filmcraft/Cargo.toml` стоит `default = []`, поэтому обычный `cargo build` даёт бинарник
  **без** панели закадрового голоса. Чтобы получить то же, что поставляется, фичу надо указать.
- **`CRAFT_FONTS_DIR`** — для сборки **не** нужен. В архиве релиза уже лежат восемь файлов
  `assets/fonts/*.ttf`, и сборка встраивает их сама. Переменная читается только
  интеграционными тестами `effectcraft-ui-egui` (`crates/ui-egui/tests/it/`); они берут чекаут
  `craft-fonts` как эталонный набор шрифтов. Нужна, только если гонять эти тесты.

Код в патчах проходит `cargo fmt`; в EffectCraft проходит и `clippy --workspace --all-targets
-- -D warnings`. В FilmCraft этот гейт красный из-за двух **предсуществующих** линтов —
`clippy::needless_bool` в `crates/hevc/src/filter.rs:506` и `unused_mut` в
`crates/engine/src/lib.rs`, — которые воспроизводятся на чистом архиве 0.20.1 и не связаны с
патчами. Подробности и доказательство — в §V.4.

### 3.2 CraftLink руками

1. Открыть проект в FilmCraft, выделить 2–3 клипа, правый клик →
   **Replace with EffectCraft Composition**.
2. EffectCraft должен открыться (или принять через control-канал) с композицией.
3. Добавить, например, Glow. **Не сохранять.**
4. Через ~1–2 секунды вернуться в FilmCraft: таймлайн должен показать уже с Glow.
5. Проверить fade-out в конце последнего клипа (регресс §1.7).
6. Закрыть и открыть оба приложения заново: связь должна сохраниться.

### 3.3 3D-стили руками

1. Композиция с рендерером **Advanced 3D** (Composition Settings ▸ Advanced).
2. Текстовый слой, 3D-переключатель включён, **Geometry Options ▸ Extrusion Depth > 0**.
3. **Layer ▸ Layer Styles ▸ Stroke** — обводка должна идти по проецируемому силуэту объёма.
4. Добавить **Inner Shadow** и **Drop Shadow** — тени должны падать от объёма, а не от плоского
   текста.
5. Включить **Per-character 3D** — обводка и тени должны облегать каждую букву.
6. Покрутить камеру/слой: стили должны «прилипать» к геометрии кадра.
7. Сравнить с выключенным GPU-ускорением: картинка должна совпадать.
8. Если не хочется собирать перед чтением: `screenshots/old-version.png` — это проваленный п. 3 в
   релизе без патча, `screenshots/new-version.png` — он же с патчем.

Это другая программа, не `craftlink-patcher.exe`, и намеренно. Патчер правит **исходники**, и ему

Он не делит код с патчером и ничего в этом пакете не меняет. Его исходники — в `installer/`, а

главным: всё, что записывает установщик, воспроизводимо из патчей.

### V.1 Если читает ИИ-ревьюер

Всё ниже устроено так, чтобы проверка шла по схеме «утверждение → файл, который его подтверждает».
Ничего не нужно принимать на веру.

| Утверждение | Где проверять |
| --- | --- |
| Связь хранится без изменения схемы | `CraftLinkSource::to_comment` / `from_comment` в `crates/engine/src/craftlink.rs` |
| Сохранять не обязательно | `Session::craftlink_tick` в `craftlink.rs` + его вызов в `crates/ui-egui/src/app/frame.rs` |
| Сохранение по-прежнему рендерит сразу | вызовы `auto_sync` в `crates/engine/src/cmd/file.rs` (только `save`, `saveAs`) |
| Открытие и revert рендер не запускают | `LIVE_IGNORED` в `craftlink.rs` |
| Экструзии со стилями идут по 2D-пути | `styled_geometry` + `needs_2d_composite` в `crates/render/src/three_d/adv.rs`; утверждается в `gpu_styled_extrusions_match_cpu` (`crates/gpu/src/tests/adv3d.rs`) |
| Стили видят слой при полной непрозрачности | деление/умножение вокруг `style_solo` в `adv.rs` |
| Стили на каждую букву существуют | `styled_buf` в `crates/render/src/styles.rs`, вызывается из `per_char_planes` в `text.rs` |
| GPU и CPU совпадают | `gpu_styled_extrusions_match_cpu` в `crates/gpu/src/tests/adv3d.rs` |
| Баг с fade-out исправлен | `nest_selection_for_bridge` в `craftlink_bridge.rs` + два регресс-теста |
| Первый запуск моста создаёт свою папку | `create_dir_all` перед `write_file` в `execute_bridge` + `the_first_bridge_run_creates_its_link_folder` |
| Подписи меню соответствуют требованию заказчика | `crates/engine/src/commands.rs` (`Send to EffectCraft…`, `Replace with EffectCraft Composition`), внутренние id остаются `clip.*CraftLink`; пункты контекстного меню и их 16 каталогов — в `crates/ui-egui/src/panels/timeline/menus.rs` и `crates/ui-egui/src/i18n/*.tsv` |

Две вещи, которые ревьюер иначе счёл бы дефектами, — обе осознанные:

1. Два `.md`-документа лежат внутри CraftLink-патчей, а не отдельным коммитом. Они описывают
   ровно эти изменения, и если их вынести, код окажется без документации в том патче, который его
   вводит. Скажет слово — вынесем отдельным патчем.
2. Стили экструзий считаются на CPU даже в GPU-пути. Это намеренно (§2.3): это тот же код, что
   выполняется для обычного 2D-слоя, поэтому тест паритета и проходит с расхождением 0.000 %.

### V.2 Как патчи проверялись

Патчи сгенерированы сравнением рабочего дерева с **чистыми релизными архивами**
(`filmcraft-0.20.1.zip`, `effectcraft-0.24.1.zip`). Затем каждый патч был применён к заново
распакованному чистому архиву, и результат **побайтово** сравнён с рабочим деревом (с
нормализацией переводов строк) — совпадение полное. Ни один **кодовый** файл не входит в два патча, и ни один файл не патчится дважды в одном
репозитории. Два документа (`CRAFTLINK_ARCHITECTURE.md`, `DYNAMIC_LINK_INTEGRATION.md`)
намеренно присутствуют в обоих CraftLink-патчах: каждая сторона связи получает свою копию в
корне своего репозитория — патч 01 кладёт их в дерево FilmCraft, патч 02 в дерево EffectCraft.

Переводы строк нормализованы к LF (в архивах релиза они LF; на диске часть файлов была CRLF).
Поэтому в патчах нет «пустых» диффов на тысячи строк из-за `\r\n`.

Тот же гейт прогнан заново после добавления исправления `os error 3` (§1.9), и отдельно проверен
регресс-тест: если убрать `create_dir_all`, тест падает ровно с `os error 3`; если вернуть — проходит.

Патчи — обычный unified diff: без строк `diff --git` и `index`, `/dev/null` для создаваемых файлов,
поэтому их читают `git apply`, `patch -p1` и `applypatch`. На этой машине `git` и `patch` не
установлены, так что побайтовый гейт выше выполнен небольшим независимым применением патча:
он расходует ровно те количества строк, которые объявлены в каждом заголовке `@@`. Все хунки во
всех трёх патчах сходятся.

### V.3 Как лучше отправлять (рекомендация)

Ниже — то, о чём просил: **как скинуть так, чтобы разработчику было понятно**.

**Главное правило: разделите два независимых изменения.** CraftLink и 3D-стили не связаны
кодом, у них разные файлы. Если сложить всё в один патч, ревьюер будет читать 1200 строк кода сразу и
не сможет принять одну часть, отложив другую. Поэтому в пакете три патча, а не один.

**Порядок сообщения (что писать в тексте, а не в файлах).** Самая частая ошибка — прислать
архив без легенды, и ревьюер тратит полчаса на выяснение, что где. Предлагаю такую структуру
письма/сообщения:

1. **Одна строка сути** — что изменилось для пользователя, без технических деталей.
2. **Две-три строки на каждую часть** — что именно и зачем.
3. **Что приложено** — список файлов пакета с одной строкой пояснения на каждый.
4. **Как применить** — точные команды.
5. **Чем проверить** — конкретные шаги в приложении.
6. **Что падает и почему это не моя вина** — сразу, чтобы не тратили время на разбор
   (blender/python3 и локаль). Это важнее, чем кажется: иначе первое, что увидит человек —
   красный тест — и решит, что патч сломан.
7. **Известные ограничения** — честно, чтобы не выглядело как «всё идеально».

Готовый текст для копирования лежит рядом: **`СООБЩЕНИЕ-РАЗРАБОТЧИКУ.txt`**.
Английская версия письма — `MESSAGE-TO-DEVELOPER.txt`, английская версия этого отчёта —
`REPORT.md`. Если разработчик не читает по-русски, отправляйте именно их.

**Формат вложения.** По убыванию удобства для получателя:

| Способ | Когда хорош | Минусы |
| --- | --- | --- |
| **Git-ветка / PR** (если есть доступ к репозиторию) | идеальный вариант: ревью по файлам, комментарии, CI | нужен доступ; у нас репозиторий локальный, без `.git` |
| **Один `.zip` с патчами + отчётом + `craftlink-patcher.exe`** (то, что лежит здесь) | получатель патчит папку одной командой и может откатиться | нужен Windows; exe без подписи |
| **Один `.zip` с патчами + отчётом** | получатель применит `git apply` и увидит настоящий дифф | нужен `git` или `patch` |
| **Один сводный `.patch`** | если человек любит `patch -p1` и один файл | 1200 строк кода в одном файле, сложно ревьюить по частям |
| **Готовые файлы целиком** (`changed-files/`) | если у получателя **точно та же** версия 0.20.1 / 0.24.1 | при малейшем расхождении версий затрёт чужие правки |

Практично отправить **zip с патчами, `changed-files/` и `craftlink-patcher.exe` внутри**: получатель
выберет, применять дифф, запустить один exe или просто заменить файлы.

**Что приложить сверх кода.** Для CraftLink — ничего особенного, он проверяется по шагам. Для
3D-стилей пара «до/после» уже лежит в пакете, в `screenshots/`, потому что «обводка идёт по силуэту»
словами не проверишь:

- `screenshots/old-version.png` — EffectCraft 0.24.1 без патча: 3D-текст с Geometry Options ▸
  Extrusion Depth, Layer Styles ▸ Stroke включён (Size 3.0, Position Outside, красный), а обводка
  **не нарисована вообще**. Всё красное в этом кадре — это рамка выделения слоя во вьюере.
- `screenshots/new-version.png` — такой же слой с этим патчем: красная обводка идёт по проекции
  силуэта каждой буквы.

Две вещи эта пара намеренно **не** доказывает, поэтому их надо сказать словами или доснять кадр,
если ревьюер попросит: камера между кадрами не вращается (ракурс разный, так что кадры
иллюстративные, а не пиксельно сравнимые), и ни в одном кадре не включён Per-character 3D. Дешевле
всего закрыть этот пробел короткой записью облёта камеры и вторым кадром с Per-character 3D — обе
вещи переключаются на обычном текстовом слое.

Скриншоты лучше класть в тот же zip (`screenshots/`), а не отдельным сообщением — так они не
потеряются.

**Именование файлов.** Патчи названы `<номер>-<продукт>-<тема>.patch`. Нумерация задаёт порядок
применения, продукт — к какому репозиторию, тема — что ревьюить. Если переименуете, сохраните эти
три части: они экономят получателю больше времени, чем любое описание.

**Чего избегать:**

- Не присылать только скриншоты без кода и наоборот.
- Не присылать патч без указания базовой версии — «применяется к 0.20.1 / 0.24.1» должно быть
  в первой строке сообщения.
- Не смешивать в одном коммите/патче `CRAFTLINK_ARCHITECTURE.md` (документация) с кодом, если
  ревьюер просит разделить — хотя здесь это осознанно: документ описывает ровно эти изменения.

### V.4 Что прогонялось перед сборкой пакета (чтобы не верить на слово)

Каждое утверждение отчёта перепроверено по исходникам непосредственно перед сборкой пакета.
Вот точные команды и результаты:

| Гейт | Команда | Результат |
| --- | --- | --- |
| Форматирование | `cargo fmt --all --check` | чисто в обоих репозиториях (чистые 0.20.1 / 0.24.1 тоже чисты, так что это настоящий гейт, а не исключение) |
| Линты, EffectCraft | `cargo clippy --workspace --all-targets -- -D warnings` | **проходит**, код возврата 0 |
| Линты, FilmCraft | `cargo clippy --workspace --all-targets -- -D warnings` | **падает, и падает так же на чистом архиве 0.20.1** — см. пояснение ниже |
| Линты по файлам патча | `cargo clippy -p filmcraft-engine -p effectcraft-engine -p effectcraft-render -p effectcraft-gpu -p effectcraft-ui-egui --all-targets` | ни одна диагностика не указывает на файл, добавленный или изменённый патчами |
| Тесты CraftLink | `cargo test -p filmcraft-engine craftlink` | 6 passed |
| Тесты CraftLink | `cargo test -p effectcraft-engine craftlink` | 10 passed |
| Тесты 3D-стилей | `cargo test -p effectcraft-render --lib` | 405 passed, 1 ignored |
| Паритет GPU | `cargo test -p effectcraft-gpu` | 310 passed, 2 ignored |
| Целостность патчей | каждый патч применён к заново распакованному архиву релиза | побайтово совпадает с рабочим деревом |
| Вывод патчера | `craftlink-patcher.exe apply` на заново распакованных архивах, затем побайтовое сравнение с рабочим деревом | 27/27 и 22/22 файла идентичны |
| Патчер отказывает чужому релизу | `apply` на папке, которая только выглядит релизом | код 1, в сообщении строка, **ничего не записано** |
| Патчер отказывает portable-сборке | `apply` на настоящей папке `*-windows-x64-portable` | код 1, объясняет, что там собранный exe, и даёт путь «патч → сборка → копирование», **ничего не записано** |
| Откат патчера | `revert` на пропатченном дереве | 23/23 заменённых файла вернулись к байтам из архива |
| Полное удаление патчера | `uninstall` на пропатченном дереве, затем сравнение дерева целиком с релизом | было 3487 файлов, стало 3487; **0 пропавших, 0 лишних, 0 изменённых** |
| Патчер не устарел | три патча и `FILES.txt` ищутся внутри exe | все четыре есть побайтово, то есть бинарник собран из этих самых файлов |

**Про линт-гейт FilmCraft — прочитайте это, это единственный красный пункт.**

`AGENTS.md` требует `cargo xtask ci`, а это `cargo fmt --check` и затем
`cargo clippy --workspace --all-targets -- -D warnings`. На этой машине такой прогон clippy
останавливается на **одном** линте в `crates/hevc/src/filter.rs:506`:

```
error: this `if` guard returns a bool literal and is followed by another
   --> crates/hevc/src/filter.rs:506:9
```

Это **предсуществующий** линт, не наш. Доказательство: если распаковать `filmcraft-0.20.1.zip`
и прогнать ту же команду на нетронутом архиве, получается ровно та же ошибка. Строка патчами не
меняется — `filmcraft-hevc` не входит в те 27 файлов, которые они трогают.

Почему это вообще всплывает: линт (`clippy::needless_bool`, более новое уточнение) срабатывает на
локально установленном Rust 1.100.0, тогда как проект объявляет `rust-version = "1.95"`. На
компиляторе, под который рассчитан проект, гейт по workspace зелёный.

Второй предсуществующий линт тоже присутствует и под `-D warnings` тоже является ошибкой:
`unused_mut` на `let mut dir = std::fs::DirBuilder::new();` в помощнике временной папки —
`crates/engine/src/lib.rs:129` в патченном дереве (`:126` в чистом архиве, потому что патч
регистрирует модуль выше). Он срабатывает только когда `filmcraft-hevc` не компилируется по пути,
и тоже воспроизводится на нетронутом архиве.

Осознанное решение: эти два линта **не тронуты**. Правка `filmcraft-hevc` смешала бы посторонний
фикс с патчем, который должен быть про CraftLink. Если нужен зелёный `cargo xtask ci` на этом
тулчейне — это правка на две строки; скажите слово, и она уйдёт отдельным четвёртым патчем.

Три падения тестов `effectcraft`, описанные в части IV, тоже только из-за окружения (`python3` и
системная локаль) и воспроизводятся на чистом чекауте без этих патчей.

### V.5 Патчи соблюдают правила репозитория

Это стоит сказать явно, потому что `AGENTS.md` — первое место, куда посмотрит ревьюер:

- **Никогда не паниковать** — ни `unwrap()`, ни `expect()`, ни `panic!`, `unreachable!`, `todo!`,
  `unimplemented!`, ни `unsafe` в добавленном нетстовом коде. Проверено сканированием каждого
  затронутого файла вне модуля `#[cfg(test)]`.
- **Узкие, покрытые тестами правки** — у бага с fade-out (§1.7) два регресс-теста, падающих без
  исправления; у бага с отсутствующей папкой (§1.9) — один; у 3D-стилей три CPU-теста и один
  GPU-тест паритета.
- **Всё есть команда** — пункты FilmCraft зарегистрированы в `commands.rs` с id, подписями и
  параметрами; внутренние id сохранили согласованные имена (`clip.replaceWithCraftLink`,
  `clip.sendToCraftLink`, `craftlink.refresh`), изменились только видимые подписи.
- **Без изменения схемы** — связь живёт в существующем поле `Item.comment`, поэтому старые проекты
  и старые сборки продолжают загружаться.
- **Без новых зависимостей** — патчи не добавляют ни одной, список разрешённых лицензий не затронут.

## ЧАСТЬ VI. Как применять патчи

### Вариант 0 — `craftlink-patcher.exe` (ничего устанавливать не нужно)

Самый простой путь и тот, что задуман для быстрой локальной проверки: три патча и `FILES.txt`
скомпилированы внутрь exe, поэтому ему не нужны ни `git`, ни `patch`, ни Python, ни сеть, ни
соседние файлы.

```
craftlink-patcher.exe                     интерактивно: покажет, что изменится, и спросит
craftlink-patcher.exe check <папка>       пробный прогон; ничего не пишет
craftlink-patcher.exe apply <папка>       прогоняет проверку, затем патчит (спрашивает перед записью)
craftlink-patcher.exe uninstall <папка>   вернуть папку ровно в исходное состояние
craftlink-patcher.exe revert <папка>      вернуть только перезаписанные файлы
craftlink-patcher.exe list                показать встроенные патчи
craftlink-patcher.exe help                справка
```

`<папка>` — корень распакованного релиза, то есть папка, в которой лежит
`apps/filmcraft/Cargo.toml` или `apps/effectcraft/Cargo.toml`. Релиз определяется по этому файлу;
папку можно просто перетащить в окно консоли.

**Не установленная и не portable версия.** В portable-папке лежит уже собранный
`filmcraft.exe` / `effectcraft.exe`, а эти патчи правят исходники (`.rs`, `.tsv`, `.md`), после
чего приложение надо пересобрать. Если указать такую папку, патчер откажется и объяснит путь:
пропатчить исходники, выполнить `cargo build --release`, затем скопировать
`target/release/<product>.exe` поверх файла в portable-папке (старый сохранить как бэкап).
То же относится к установке, которую сделал лаунчер.

Защита намеренно строже, чем у `patch -p1`:

- **`check` ничего не пишет.** Все хунки применяются только в памяти.
- **`apply` сначала планирует, потом пишет.** Если хотя бы одна строка контекста где-то не
  совпала, он останавливается и не трогает ничего — полупатч на чужой папке невозможен. В
  сообщении есть файл, строка, что ожидалось и что найдено.
- **Каждый перезаписываемый файл сначала копируется в `_craftlink-backup/<дата>/`** внутри папки
  релиза, а имена *созданных* файлов записываются в ту же папку, поэтому откат получается полным,
  а не частичным.
- **После записи каждый файл сверяется по sha256** со встроенным `FILES.txt` — строка
  `Verified against FILES.txt: 25 file(s) ok` (FilmCraft) или `20` (EffectCraft), плюс два корневых
  документа, которых в манифесте нет. Расхождение — ошибка, а не предупреждение.
- **`uninstall` — настоящий откат:** возвращает перезаписанные файлы, удаляет добавленные и
  подчищает опустевшие папки, то есть дерево возвращается в состояние релиза. Проверено сравнением
  дерева целиком: было 3487 файлов, стало 3487, **ни одного пропавшего, лишнего или изменённого**.
  Файл, который пользователь правил после патча, намеренно остаётся и называется в выводе.
- `revert` — узкий вариант: возвращает только перезаписанные файлы, добавленные оставляет на месте
  и пишет об этом.

Ожидаемые числа: `27` записанных файлов для FilmCraft (23 замены + 4 новых) и `22` для EffectCraft
(19 замен + 3 новых); два `.md`-документа входят в новые с обеих сторон. Удалить
`_craftlink-backup/` можно без последствий, как только сборка и тесты зелёные.

Если патчи будут перегенерированы, exe надо пересобрать — он носит их копию внутри.
Пересборка: `cd patcher && cargo build --release`; читает патчи из корня пакета, нужен только
Rust-тулчейн и сеть не нужна. `cargo test` в той же папке прогоняет двенадцать тестов: два падают,
если патч и встроенный `FILES.txt` разойдутся, один — если патч перестанет разбираться, и ещё один
держит текст отказа для portable-сборки.

### Вариант 0б — `CraftLink-Installer.exe` (без Rust, для конечных пользователей)

`craftlink-patcher.exe` правит исходники, поэтому ему всё равно нужен `cargo`, чтобы превратить их
в программу. Для человека без Rust — а вне проекта он почти у всех — это и есть вся сложность.
`CraftLink-Installer.exe` её убирает: две готовые сборки скомпилированы внутрь exe через
`include_bytes!`, поэтому он ставит, ничего не собирая.

Лежит в `craftlink-quick-patch/`, исходники здесь — в `installer/`.

```
CraftLink-Installer.exe                     интерактивно: найдёт, покажет, спросит
CraftLink-Installer.exe check <папка>       пробный прогон; сообщает, что будет заменено
CraftLink-Installer.exe install <папка>     заменить программу (сначала бэкап)
CraftLink-Installer.exe uninstall <папка>   вернуть предыдущую программу
CraftLink-Installer.exe list                что лежит внутри
CraftLink-Installer.exe help                справка
```

`<папка>` — **portable**-папка: та, где `filmcraft.exe` или `effectcraft.exe` лежат рядом с
`portable.txt`. Установщик смотрит в неё, на один уровень ниже (архивы обычно распаковываются как
`имя/имя/`) и на два уровня ниже, поэтому человек может указать любой уровень. Если указать папку, в
которой лежат распакованные папки обоих продуктов, он поставит оба за один прогон. Перетаскивание
папки на exe делает то же, что и указание пути.

Что он делает и от чего отказывается:

- **Определяет по содержимому, а не по имени.** Программа, уже лежащая в папке, должна дать хеш
  официальной сборки (SHA-256 закреплён для каждого продукта); любая другая — другая версия или уже
  изменённая сборка — отклоняется, а не перезаписывается.
- **Сначала планирует всё, потом пишет.** Если хоть одна папка не подходит, прогон
  останавливается и нигде ничего не меняется, включая папки, которые подходили.
- **Меняет ровно один файл** в каждой portable-папке. `data/`, `portable.txt`, лицензии и
  `*-cli.exe` не трогаются.
- **Сначала делает бэкап** в `_craftlink-backup/<дата>/` внутри portable-папки, с `REPLACED.txt`,
  где записано, что заменено в этом прогоне; `uninstall` восстанавливает из него и проверен на
  точном возврате официальных байтов.
- **`check` ничего не пишет** вообще.

Цена — размер: внутри сборки на 72,3 МБ и 109,2 МБ, поэтому exe ~182 МБ (~67 МБ в zip). Это плата
за отсутствие компилятора.

Этих двух сборок в пакете **нет** — это результат сборки, он воспроизводится из патчей, а копии
превратили бы 5-мегабайтный пакет для ревью в 187-мегабайтный. Вместо них
`installer/payload/EMBEDDED.txt` фиксирует смещение, длину и SHA-256 каждой внутри поставляемого
установщика — этого достаточно, чтобы сверить полученный `CraftLink-Installer.exe` с пакетом:

```powershell
# обе вшитые программы, вырезанные из присланного exe, должны совпасть с EMBEDDED.txt
python - <<'PY'
import hashlib, io
exe = open("CraftLink-Installer.exe", "rb").read()
for row in io.open("craftlink-3dstyles-report/installer/payload/EMBEDDED.txt", encoding="utf-8"):
    if row.startswith("#") or row.startswith("name\t") or not row.strip():
        continue
    name, offset, length, digest = row.split("\t")
    blob = exe[int(offset):int(offset) + int(length)]
    print(name, hashlib.sha256(blob).hexdigest() == digest)
PY
```

Пересборка после смены содержимого: `cd installer && cargo build --release`. Нужны
`payload/filmcraft.exe` и `payload/effectcraft.exe` на месте — их берут из `target/release/`
пропатченных деревьев — и никакой сети. `cargo test` в этой папке гоняет пятнадцать тестов: два
вектора SHA-256, проверку, что каждая сборка — настоящий PE-файл, а не заглушка, что закреплённый
хеш релиза отличается от носимой сборки, отказ чужой сборке и правила поиска папок (прямо,
вложенно, оба продукта, пустая).

### Вариант А — git

Пакет — это папка с файлами; распакуйте два архива исходников рядом с ней, чтобы получилось так:

```
где-то/
├── 01-filmcraft-0.20.1-craftlink.patch      ← из этого пакета
├── 02-effectcraft-0.24.1-craftlink.patch    ← из этого пакета
├── 03-effectcraft-0.24.1-3d-layer-styles.patch
├── filmcraft-0.20.1/                        ← распакованный архив исходников
└── effectcraft-0.24.1/                      ← распакованный архив исходников
```

Затем:

```powershell
# Папки релизов и файлы патчей лежат рядом.
cd filmcraft-0.20.1
git apply --check ../01-filmcraft-0.20.1-craftlink.patch   # проверка без изменений
git apply         ../01-filmcraft-0.20.1-craftlink.patch

cd ../effectcraft-0.24.1
git apply --check ../02-effectcraft-0.24.1-craftlink.patch
git apply         ../02-effectcraft-0.24.1-craftlink.patch
git apply --check ../03-effectcraft-0.24.1-3d-layer-styles.patch
git apply         ../03-effectcraft-0.24.1-3d-layer-styles.patch
```

Пути в патчах в формате `a/… b/…`, поэтому `-p1` (для `git apply` это значение по умолчанию)
подходит. Два патча EffectCraft не пересекаются по файлам, поэтому их порядок не важен.

## ЧАСТЬ VIII. Известные ограничения

**CraftLink**

- **Не по-кейстроково.** Мастер перерендеривается через секунду после последней правки, по
  File ▸ Save или по `file.craftlinkSync` — не на каждый промежуточный кадр перетаскивания
  слайдера. Следующий шаг был бы покадровый кэш.
- **Нет потоковой передачи.** Задержка = время рендера всей композиции + один кадр UI.
- **Один рендер за раз.** Правка во время рендера запоминается и рендерится после.
- **Live-link только в десктопной сборке.** В браузерной версии связь живёт в папке на диске,
  а фонового потока там нет — рендер был бы встроенным.
- **`autoSync: false`** выключает и live-link; такая связь обновляется только вручную.

**3D-стили**

- Read-back на каждый стильный экструдированный слой и кадр (см. §2.6).
- Per-character стили считаются на каждую букву, а не на общий силуэт слова.
- Inner Bevel подкрашивает сглаженный край — старое поведение, не в этой работе.

**Окружение**

- Тест Blender требует рабочего `python3` в `PATH`; здесь `python3` разрешается в 0-байтовую
  заглушку Microsoft Store, которая завершается с кодом 9009 (см. ЧАСТЬ IV).
- Два UI-теста ждут английскую локаль (на машине русская).
